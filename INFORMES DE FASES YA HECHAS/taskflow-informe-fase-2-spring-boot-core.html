1. Spring Boot — Estructura y Auto-configuración
@SpringBootApplication · SpringApplication.run() · Tomcat embebido · CommandLineRunner

¿Qué es? Spring Boot es un framework que simplifica la creación de aplicaciones Spring eliminando la configuración manual. Con una sola anotación @SpringBootApplication y una llamada a SpringApplication.run(), levanta un servidor web completo.

¿Qué hace @SpringBootApplication? Es una anotación compuesta que activa tres cosas a la vez:

  • @Configuration — la clase puede definir beans
  • @EnableAutoConfiguration — Spring configura automáticamente todo lo que detecta en el classpath (Tomcat, Jackson para JSON, etc.)
  • @ComponentScan — escanea el paquete base buscando clases con @Component, @Service, @Controller, @Repository

CommandLineRunner: bean especial que Spring ejecuta automáticamente después de inicializar el contexto. Lo usamos para cargar los datos de prueba.

@SpringBootApplication  // @Configuration + @EnableAutoConfiguration + @ComponentScan
public class TaskflowApplication {

    public static void main(String[] args) {
        // Arranca el contenedor IoC + servidor Tomcat embebido en puerto 8080
        SpringApplication.run(TaskflowApplication.class, args);
    }

    // CommandLineRunner: se ejecuta automáticamente al terminar el arranque
    @Bean
    public CommandLineRunner cargarDatosDePrueba(TaskService taskService) {
        return args -> {
            // Spring inyecta taskService automáticamente — no usamos new
            taskService.crear(new Task("Preparar presentación Q3",
                Priority.ALTA, Category.TRABAJO, 1L));
            // ... más tareas de prueba
        };
    }
}

2. IoC — Inversión de Control
El contenedor Spring administra los objetos — no tú

¿Qué es? La Inversión de Control es un principio de diseño donde el control de la creación y ciclo de vida de los objetos se transfiere del programador al framework. En Spring, el contenedor IoC (ApplicationContext) crea, configura y destruye los beans.

Sin IoC vs Con IoC:

// ❌ Sin IoC — tú controlas la creación (alto acoplamiento)
public class TaskController {
    private TaskService taskService = new TaskService(); // dependencia fija
}

// ✅ Con IoC — Spring controla la creación (bajo acoplamiento)
public class TaskController {
    private final TaskService taskService;
    // Spring detecta este constructor y provee el TaskService automáticamente
    public TaskController(TaskService taskService) {
        this.taskService = taskService;
    }
}

// Spring administra el ciclo de vida completo:
// 1. Crea el TaskService (singleton por defecto)
// 2. Lo inyecta en TaskController al crear el controller
// 3. Lo destruye cuando la aplicación para

Beneficio clave: si mañana cambias TaskService por TaskServiceBD, solo cambias la definición del bean — ningún controller ni service cambia su código.

3. Dependency Injection — Inyección de Dependencias
Inyección por constructor · @Autowired implícito · beans singleton

¿Qué es? La Inyección de Dependencias es el mecanismo concreto con el que Spring implementa IoC. Cuando un bean necesita otro bean, Spring lo "inyecta" automáticamente. Hay tres formas de inyectar: por constructor (recomendada), por setter, o por campo con @Autowired.

¿Por qué por constructor? Es la práctica recomendada por Spring desde la versión 4: garantiza que el objeto nunca quede en estado inconsistente (los campos no pueden ser null), facilita los tests y permite declarar los campos como final.

// ✅ Inyección por constructor — práctica recomendada
@RestController
public class TaskController {

    private final TaskService taskService;   // final — no puede ser null
    private final AppConfig appConfig;

    // Si hay un solo constructor, @Autowired es opcional (Spring lo infiere)
    public TaskController(TaskService taskService, AppConfig appConfig) {
        this.taskService = taskService;
        this.appConfig = appConfig;
    }
}

// ❌ Inyección por campo — desaconsejada (no permite final, dificulta tests)
@Autowired
private TaskService taskService;  // puede ser null si algo falla

4. @Configuration y @Bean
AppConfig.java — definición explícita de beans administrados por Spring

¿Qué es? @Configuration marca una clase como fuente de definiciones de beans. Cada método anotado con @Bean retorna un objeto que Spring registra en su contenedor y administra como singleton.

¿Cuándo usar @Bean vs @Service/@Component? Usamos @Bean cuando necesitamos control explícito sobre cómo se crea el objeto, o cuando la clase es de una librería externa que no podemos anotar. Usamos @Service para nuestras propias clases de servicio.

@Configuration
public class AppConfig {

    // @Bean explícito — Spring administra esta instancia como singleton
    // Cualquier clase que necesite TaskService lo recibe inyectado
    @Bean
    public TaskService taskService() {
        return new TaskService();
        // Spring llama a este método UNA SOLA VEZ
        // y reutiliza la misma instancia en toda la app (singleton)
    }
}

5. application.yml + Profiles (dev/prod)
Configuración centralizada · spring.profiles.active · sobrescritura por entorno

¿Qué es? El application.yml es el archivo central de configuración de Spring Boot. Spring lo lee automáticamente al arrancar. Los Profiles permiten tener configuraciones diferentes según el entorno: desarrollo usa H2 y logging detallado; producción usa PostgreSQL y logging mínimo.

¿Cómo funciona? Spring carga primero el application.yml base, luego sobreescribe con el archivo del perfil activo (application-dev.yml o application-prod.yml).

# application.yml — configuración base
spring:
  application:
    name: taskflow
  profiles:
    active: dev    # perfil activo por defecto

server:
  port: 8080

# Propiedades personalizadas inyectables con @Value
taskflow:
  app:
    max-tareas-por-usuario: 100
    version: "1.0.0"
    mensaje-bienvenida: "Bienvenido a TaskFlow API"

---
# application-dev.yml — sobreescribe solo lo necesario para dev
spring:
  config:
    activate:
      on-profile: dev
logging:
  level:
    com.taskflow: DEBUG   # logging detallado en desarrollo

---
# application-prod.yml — configuración de producción
spring:
  config:
    activate:
      on-profile: prod
logging:
  level:
    com.taskflow: WARN    # solo errores en producción

6. @Value y @ConfigurationProperties
Inyectar valores del YAML en clases Java — dos enfoques complementarios

¿Qué es? Spring puede inyectar cualquier valor del application.yml directamente en campos Java. @Value es para valores individuales. @ConfigurationProperties es para mapear un bloque completo de propiedades a una clase Java tipada.

// @Value — inyecta un valor individual del YAML
@Value("${taskflow.app.mensaje-bienvenida}")
private String mensajeBienvenida;  // = "Bienvenido a TaskFlow API"

@Value("${taskflow.app.version}")
private String version;            // = "1.0.0"

// @ConfigurationProperties — mapea un bloque completo del YAML
// taskflow.app.* → campos de la clase TaskflowProperties
@ConfigurationProperties(prefix = "taskflow.app")
public static class TaskflowProperties {
    private int maxTareasPorUsuario;  // = 100
    private String version;           // = "1.0.0"
    private String mensajeBienvenida; // = "Bienvenido a TaskFlow API"
    // getters y setters...
}

// Diferencia clave:
// @Value        → un solo valor, expresión SpEL, simple
// @ConfigProps  → grupo de valores, tipado, validable con @Valid

7. Controllers, Services, Repositories — Arquitectura en capas
@RestController · @Service · @Repository · separación de responsabilidades

¿Qué es? Spring Boot promueve una arquitectura de 3 capas donde cada una tiene una responsabilidad única. Esto sigue el principio Single Responsibility de SOLID.

  • Controller (@RestController) — recibe peticiones HTTP, delega al Service, retorna respuestas JSON. No tiene lógica de negocio.
  • Service (@Service) — contiene la lógica de negocio. No sabe nada de HTTP ni de base de datos.
  • Repository (@Repository) — accede a la base de datos. En Fase 2 aún usamos el Map en memoria; en Fase 4 usará JPA.
// Capa Controller — solo maneja HTTP
@RestController          // = @Controller + @ResponseBody (retorna JSON)
@RequestMapping("/api/tareas")  // ruta base de todos los endpoints
public class TaskController {

    @GetMapping           // GET /api/tareas
    public ResponseEntity<List<Task>> listarTareas() {
        return ResponseEntity.ok(taskService.listarTodas()); // 200 OK
    }

    @GetMapping("/{id}")  // GET /api/tareas/1
    public ResponseEntity<Task> obtenerTarea(@PathVariable Long id) {
        return taskService.buscarPorId(id)
            .map(ResponseEntity::ok)              // 200 si existe
            .orElse(ResponseEntity.notFound().build()); // 404 si no
    }

    @PostMapping          // POST /api/tareas
    public ResponseEntity<Task> crearTarea(@RequestBody Task tarea) {
        Task creada = taskService.crear(tarea);
        return ResponseEntity.status(HttpStatus.CREATED).body(creada); // 201
    }

    @DeleteMapping("/{id}") // DELETE /api/tareas/1
    public ResponseEntity<Void> eliminarTarea(@PathVariable Long id) {
        if (taskService.buscarPorId(id).isEmpty()) {
            return ResponseEntity.notFound().build(); // 404
        }
        taskService.eliminar(id);
        return ResponseEntity.noContent().build();  // 204
    }
}

8. ResponseEntity y códigos HTTP
200 OK · 201 Created · 204 No Content · 404 Not Found — respuestas semánticas

¿Qué es? ResponseEntity<T> permite controlar completamente la respuesta HTTP: código de estado, headers y body. Una API REST bien diseñada usa el código HTTP correcto para cada situación.

// 200 OK — solicitud exitosa con datos
ResponseEntity.ok(lista)

// 201 Created — recurso creado exitosamente
ResponseEntity.status(HttpStatus.CREATED).body(tareaCreada)

// 204 No Content — operación exitosa sin datos que retornar
ResponseEntity.noContent().build()

// 404 Not Found — recurso no existe
ResponseEntity.notFound().build()

// Patrón con Optional — retorna 200 o 404 automáticamente
taskService.buscarPorId(id)
    .map(ResponseEntity::ok)              // si existe → 200 + body
    .orElse(ResponseEntity.notFound().build()); // si no → 404

Resumen de códigos usados:

  • 200 OK → GET exitoso con datos
  • 201 Created → POST que crea un recurso nuevo
  • 204 No Content → DELETE exitoso
  • 404 Not Found → recurso no encontrado

9. Spring Boot Actuator
/actuator/health · /actuator/info · /actuator/metrics · /actuator/beans

¿Qué es? Actuator añade endpoints automáticos de monitoreo y gestión a cualquier aplicación Spring Boot. Sin escribir ningún código, expone información sobre el estado de la app, métricas, beans registrados y más.

¿Para qué sirve en producción? Los orquestadores como Kubernetes usan /actuator/health para saber si el pod está listo para recibir tráfico (liveness/readiness probes — lo veremos en Fase 9).

# application.yml — configurar qué endpoints exponer
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,beans,env
  endpoint:
    health:
      show-details: always   # muestra detalles de cada componente
  info:
    env:
      enabled: true          # expone el bloque "info:" del YAML

# Datos que aparecen en /actuator/info
info:
  app:
    name: TaskFlow API
    version: "1.0.0"
    fase-actual: "Fase 2 - Spring Boot Core"

Endpoints disponibles:

  • /actuator/health → estado UP/DOWN de la aplicación
  • /actuator/info → metadatos del proyecto (version, descripción)
  • /actuator/metrics → métricas de JVM, HTTP, memoria
  • /actuator/beans → todos los beans registrados en Spring
  • /actuator/env → todas las propiedades de configuración

10. @PathVariable y @RequestParam
Parámetros de URL · Query strings · Filtros dinámicos desde HTTP

¿Qué es? Son dos formas de recibir datos del cliente en la URL. @PathVariable extrae un segmento de la ruta (/tareas/1). @RequestParam extrae parámetros de query string (/tareas?estado=PENDIENTE).

// @PathVariable — el valor va en la ruta
// GET /api/tareas/42
@GetMapping("/{id}")
public ResponseEntity<Task> obtenerTarea(@PathVariable Long id) {
    // id = 42
}

// @RequestParam — el valor va en el query string
// GET /api/tareas?estado=PENDIENTE&categoria=TRABAJO
@GetMapping
public ResponseEntity<List<Task>> listarTareas(
        @RequestParam(required = false) String estado,
        @RequestParam(required = false) String categoria) {
    // estado = "PENDIENTE", categoria = "TRABAJO"
    // required=false → el parámetro es opcional, puede ser null
}

// Diferencia clave:
// @PathVariable  → identifica un recurso específico (/tareas/42)
// @RequestParam  → filtra o modifica la consulta (/tareas?estado=PENDIENTE)
