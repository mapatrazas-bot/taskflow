🎯 ¿Qué es TaskFlow?
TaskFlow es una API REST empresarial para la gestión y categorización de tareas personales y laborales. Permite operaciones CRUD completas, estados controlados (PENDIENTE, EN_PROGRESO, COMPLETADA, CANCELADA), prioridades, categorías, filtrado dinámico mediante JPA Specifications, paginación, auditoría automática de fechas, autenticación/autorización mediante tokens JWT y documentación interactiva con OpenAPI 3 / Swagger.

En la Fase 7 transformamos la aplicación en un paquete de producción autocontenido, dockerizado y automatizado con integración continua, listo para ser desplegado en cualquier entorno y presentado como portafolio en GitHub.

📚 Conceptos Aplicados — Explicación y Código

1 Maven Lifecycle y Fat JAR (Packaging)

¿Qué es? Maven organiza la compilación en fases ordenadas: validate → compile → test → package. El plugin spring-boot-maven-plugin intercepta la fase package y reempaqueta las clases junto con todas las dependencias y un servidor Tomcat embebido en un único archivo Fat JAR (o Uber JAR).

¿Dónde se aplicó? En pom.xml y ejecutado mediante el Maven Wrapper (.\mvnw.cmd clean package), generando taskflow-0.0.1-SNAPSHOT.jar.

<!-- taskflow/pom.xml -->
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>
2 Docker Multi-Stage Build

¿Qué es? Una técnica de Docker donde se utilizan múltiples instrucciones FROM en un solo Dockerfile. La primera etapa (Builder) compila el código con el JDK completo, mientras que la segunda etapa (Runtime) usa un JRE mínimo y solo copia el artefacto .jar resultante.

¿Por qué importa? Reduce drásticamente el tamaño de la imagen (de ~800MB a ~250MB), previene la exposición del código fuente y mejora la seguridad al no incluir compiladores ni herramientas innecesarias en producción.

# ETAPA 1: Builder (JDK 21 completo para compilar)
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app
COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN chmod +x ./mvnw
RUN ./mvnw dependency:go-offline -B
COPY src ./src
RUN ./mvnw clean package -DskipTests -B

# ETAPA 2: Runtime (JRE 21 ligero para producción)
FROM eclipse-temurin:21-jre-alpine AS runtime
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --from=builder /app/target/taskflow-*.jar app.jar
RUN chown -R appuser:appgroup /app
USER appuser
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
3 Docker Compose & Networking

¿Qué es? Herramienta para definir y correr aplicaciones multi-contenedor. Crea una red virtual compartida donde los contenedores se resuelven por su nombre de servicio (DNS interno de Docker).

¿Dónde se aplicó? En docker-compose.yml, levantando PostgreSQL 16 Alpine en el puerto 5432 y la API TaskFlow en el puerto 8080, usando healthcheck para sincronizar el arranque.

services:
  postgres-db:
    image: postgres:16-alpine
    container_name: taskflow-postgres
    environment:
      POSTGRES_DB: taskflow_db
      POSTGRES_USER: taskflow_user
      POSTGRES_PASSWORD: taskflow_secret
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U taskflow_user -d taskflow_db"]
      interval: 5s

  taskflow-api:
    build: .
    container_name: taskflow-app
    depends_on:
      postgres-db:
        condition: service_healthy
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres-db:5432/taskflow_db
4 Spring Profiles e Inyección de Variables de Entorno

¿Qué es? La sintaxis ${VARIABLE:valor_por_defecto} en YAML permite que Spring Boot lea parámetros del entorno del contenedor o utilice un valor fallback si no se especifican.

¿Dónde se aplicó? En application-prod.yml para parametrizar la URL de la base de datos, credenciales y clave JWT.

# taskflow/src/main/resources/application-prod.yml
spring:
  datasource:
    url: ${SPRING_DATASOURCE_URL:jdbc:postgresql://localhost:5432/taskflow_db}
    username: ${SPRING_DATASOURCE_USERNAME:taskflow_user}
    password: ${SPRING_DATASOURCE_PASSWORD:taskflow_secret}
  jpa:
    hibernate:
      ddl-auto: none  # Flyway maneja las tablas
5 CI/CD Pipeline con GitHub Actions

¿Qué es? Integración continua automatizada en la nube de GitHub. Ejecuta un runner en cada git push para garantizar que ningún cambio rompa los tests antes de fusionar código.

¿Dónde se aplicó? En .github/workflows/ci.yml.

name: TaskFlow CI/CD Pipeline
on:
  push:
    branches: [ main, develop ]
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven
      - run: cd taskflow && ./mvnw clean test
      - run: cd taskflow && docker build -t taskflow-api:test .

⚠️ Hallazgo Técnico Crítico y Solución

Problema: SchemaManagementException: Schema validation: missing table [tasks]

Al arrancar la aplicación en PostgreSQL nuevo mediante Docker Compose, Hibernate intentaba validar las tablas con ddl-auto: validate antes de que Flyway ejecutara las migraciones V1__crear_tablas.sql. Como la BD estaba vacía, la validación fallaba y el contenedor de Spring Boot entraba en bucle de reinicio.

Solución: Desactivar la validación automática de Hibernate con ddl-auto: none

Se modificó spring.jpa.hibernate.ddl-auto: none en application-prod.yml. Esto permite que el bean de Flyway ejecute las migraciones versionadas (V1 creación de tablas, V2 datos demo, V3 seguridad) de manera ordenada y segura al arrancar.

🔗 Cómo se Relacionan los Conceptos

Maven Wrapper (mvnw)
→
Garantiza versiones idénticas de Maven en local, dentro de Docker y en el runner de GitHub Actions sin requerir instalación previa.
Multi-Stage Dockerfile
→
Separa la etapa pesada de compilación (JDK) de la etapa ligera de producción (JRE Alpine), protegiendo el código fuente.
Docker Compose Healthcheck
→
Comprueba pg_isready antes de iniciar Spring Boot, evitando fallos de conexión tempranos.
Spring Profile prod
→
Inyecta credenciales y URL de PostgreSQL desde las variables de entorno definidas en el compose.
