1. DTOs — Data Transfer Objects (Request / Response separados)
CrearTareaRequest · ActualizarTareaRequest · CambiarEstadoRequest · TareaResponse

¿Qué es? Un DTO es una clase cuyo único propósito es transportar datos entre el cliente HTTP y el servidor. No es la entidad de dominio — es una representación adaptada para la API.

¿Por qué separar Request de Response?

  • Request — lo que el cliente envía: solo los campos que el cliente puede escribir, con validaciones.
  • Response — lo que el servidor retorna: puede incluir campos calculados (estaVencida, diasRestantes, estadoEtiqueta) que el cliente nunca envía.
  • Podemos cambiar el modelo de dominio sin romper la API y viceversa.
  • Nunca exponemos campos internos (como passwordHash) accidentalmente.
// DTO Request (entrada) — solo lo que el cliente puede enviar
public class CrearTareaRequest {
    @NotBlank private String titulo;
    @NotNull  private Priority prioridad;
    @Future   private LocalDate fechaLimite; // opcional
    // sin id, sin fechaCreacion, sin estado
}

// DTO Response (salida) — lo que el servidor retorna
public class TareaResponse {
    private Long id;
    private String titulo;
    private String estadoEtiqueta; // campo calculado: "En progreso"
    private boolean estaVencida;   // campo calculado
    private long diasRestantes;    // campo calculado
    private LocalDateTime fechaCreacion;

    // Factory method — convierte entidad de dominio al DTO
    public static TareaResponse fromTask(Task task) {
        TareaResponse dto = new TareaResponse();
        dto.id = task.getId();
        dto.estadoEtiqueta = task.getStatus().getEtiqueta();
        dto.estaVencida = task.estaVencida();   // calculado
        dto.diasRestantes = task.diasRestantes(); // calculado
        return dto;
    }
}

2. Bean Validation — @Valid + anotaciones
@NotBlank · @NotNull · @Size · @Future · @Min — validación declarativa

¿Qué es? Bean Validation (Jakarta Validation) permite declarar reglas de validación directamente en los campos de los DTOs con anotaciones. Spring las evalúa automáticamente cuando el controller recibe una petición con @Valid.

¿Por qué es mejor que validar manualmente? Sin Bean Validation tendríamos if (titulo == null || titulo.isBlank()) en cada método del controller. Con anotaciones, la regla está junto al dato y Spring la aplica automáticamente.

// 1. Declarar reglas en el DTO con anotaciones
public class CrearTareaRequest {

    @NotBlank(message = "El título es obligatorio")
    @Size(min = 3, max = 100, message = "Entre 3 y 100 caracteres")
    private String titulo;

    @NotNull(message = "La prioridad es obligatoria")
    private Priority prioridad;

    @Future(message = "La fecha límite debe ser futura")
    private LocalDate fechaLimite; // opcional pero si se envía debe ser futura
}

// 2. Activar la validación en el controller con @Valid
@PostMapping
public ResponseEntity<TareaResponse> crearTarea(
        @Valid @RequestBody CrearTareaRequest request) {
    // Si llega aquí, el DTO ya pasó todas las validaciones
    // Si algo falla, Spring lanza MethodArgumentNotValidException
    // que captura nuestro GlobalExceptionHandler → 400 Bad Request
}

// Anotaciones disponibles:
// @NotNull    → no puede ser null
// @NotBlank   → no puede ser null, vacío ni espacios
// @NotEmpty   → no puede ser null ni vacío (permite espacios)
// @Size       → longitud min/max para String o colecciones
// @Min/@Max   → valor numérico mínimo/máximo
// @Future     → fecha debe ser en el futuro
// @Past       → fecha debe ser en el pasado
// @Email      → formato de email válido
// @Pattern    → expresión regular

3. Exception Handling Global — @RestControllerAdvice
GlobalExceptionHandler · ApiError · manejo centralizado de errores

¿Qué es? @RestControllerAdvice es una clase especial de Spring que intercepta todas las excepciones lanzadas por cualquier controller. Sin esto, una excepción no controlada retornaría un error genérico 500 con el stack trace al cliente — lo cual es un problema de seguridad y usabilidad.

Flujo: Controller lanza excepción → Spring la intercepta en GlobalExceptionHandler → retorna JSON con formato ApiError consistente.

@RestControllerAdvice  // intercepta excepciones de TODOS los controllers
public class GlobalExceptionHandler {

    // Handler 1: errores de @Valid — campo inválido → 400
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> manejarValidacion(
            MethodArgumentNotValidException ex, HttpServletRequest req) {

        // Extrae todos los errores de campo con Streams
        List<ApiError.ErrorDetalle> detalles = ex.getBindingResult()
            .getFieldErrors().stream()
            .map(e -> new ApiError.ErrorDetalle(e.getField(), e.getDefaultMessage()))
            .collect(Collectors.toList());

        ApiError error = new ApiError(400, "Validación fallida",
            "VALIDATION_ERROR", req.getRequestURI());
        error.setErroresDetalle(detalles);
        return ResponseEntity.badRequest().body(error);
    }

    // Handler 2: excepciones de dominio (TaskNotFoundException, etc.)
    @ExceptionHandler(ApiException.class)
    public ResponseEntity<ApiError> manejarApiException(
            ApiException ex, HttpServletRequest req) {
        // Usa el httpStatus que definimos en la excepción (Fase 1)
        ApiError error = new ApiError(ex.getHttpStatus(), ex.getMessage(),
            ex.getCodigoError(), req.getRequestURI());
        return ResponseEntity.status(ex.getHttpStatus()).body(error);
    }

    // Handler 3: cualquier excepción no controlada → 500
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> manejarGeneral(Exception ex, ...) {
        // Nunca exponemos el stack trace al cliente
        return ResponseEntity.internalServerError()
            .body(new ApiError(500, "Error interno", "INTERNAL_ERROR", ...));
    }
}

Respuesta de error estándar (ApiError):

"timestamp": "2026-08-27T14:30:00", "status": 400, "error": "Validación fallida", "codigoError": "VALIDATION_ERROR", "path": "/api/tareas", "erroresDetalle": [ { "campo": "titulo", "mensaje": "El título es obligatorio" }, { "campo": "prioridad", "mensaje": "La prioridad es obligatoria" } ]

4. Todos los verbos HTTP — GET, POST, PUT, PATCH, DELETE
Semántica REST correcta para cada operación

¿Cuándo usar cada verbo? Cada verbo HTTP tiene una semántica específica en REST:

  • GET — leer datos, sin efectos secundarios, idempotente
  • POST — crear un recurso nuevo, no idempotente
  • PUT — reemplazar un recurso completo, idempotente
  • PATCH — actualizar parcialmente (solo los campos enviados)
  • DELETE — eliminar un recurso, idempotente
// GET — leer (no modifica nada)
@GetMapping           // GET /api/tareas
@GetMapping("/{id}") // GET /api/tareas/1

// POST — crear recurso nuevo → 201 Created
@PostMapping          // POST /api/tareas
public ResponseEntity<TareaResponse> crearTarea(
        @Valid @RequestBody CrearTareaRequest request) {
    return ResponseEntity.status(HttpStatus.CREATED).body(...);
}

// PUT — reemplazar completo → todos los campos son obligatorios
@PutMapping("/{id}")  // PUT /api/tareas/1
public ResponseEntity<TareaResponse> actualizarTarea(
        @PathVariable Long id,
        @Valid @RequestBody ActualizarTareaRequest request) { ... }

// PATCH — actualización parcial → solo el estado
@PatchMapping("/{id}/estado") // PATCH /api/tareas/1/estado
public ResponseEntity<TareaResponse> cambiarEstado(
        @PathVariable Long id,
        @Valid @RequestBody CambiarEstadoRequest request) { ... }

// DELETE — eliminar → 204 No Content (sin body)
@DeleteMapping("/{id}") // DELETE /api/tareas/1
public ResponseEntity<Void> eliminarTarea(@PathVariable Long id) {
    taskService.eliminar(id);
    return ResponseEntity.noContent().build(); // 204
}

5. ResponseEntity + HTTP Status Codes
200 · 201 · 204 · 400 · 404 · 409 · 500 — respuestas semánticas completas

¿Por qué importa el código HTTP correcto? El cliente (Postman, frontend, otra API) usa el código HTTP para saber qué ocurrió sin leer el body. Un 200 siempre significa éxito; un 404 siempre significa "no existe".

// 200 OK — petición exitosa con datos
ResponseEntity.ok(tareaResponse)

// 201 Created — recurso creado → incluir el recurso creado en el body
ResponseEntity.status(HttpStatus.CREATED).body(tareaCreada)

// 204 No Content — operación exitosa sin datos que retornar (DELETE)
ResponseEntity.noContent().build()

// 400 Bad Request — datos inválidos (generado por GlobalExceptionHandler)
// 404 Not Found — recurso no existe (TaskNotFoundException → ApiError)
// 409 Conflict — conflicto de estado (TaskStateException → ApiError)
// 500 Internal Server Error — error no controlado

// Con headers personalizados
HttpHeaders headers = new HttpHeaders();
headers.add("X-Total-Count", String.valueOf(totalElementos));
ResponseEntity.ok().headers(headers).body(pageResponse);

6. Headers HTTP personalizados
X-Total-Count · HttpHeaders · respuesta con metadatos en el header

¿Qué es? Los headers HTTP permiten enviar metadatos adicionales con la respuesta sin incluirlos en el body JSON. El header personalizado X-Total-Count es un patrón estándar para enviar el total de elementos en listados paginados.

// Agregar header personalizado a la respuesta
HttpHeaders headers = new HttpHeaders();
headers.add("X-Total-Count", String.valueOf(pageResult.totalElementos()));

// También exponemos el header con CORS para que el frontend pueda leerlo
// (en WebConfig.java)
registry.addMapping("/api/**")
    .exposedHeaders("X-Total-Count");  // permite que JS del browser lo lea

// En Postman: pestaña Headers de la respuesta
// X-Total-Count: 5

7. CORS — Cross-Origin Resource Sharing
WebConfig · addCorsMappings · seguridad del navegador

¿Qué es? Los navegadores web bloquean por seguridad las peticiones HTTP desde un origen diferente al del servidor (política Same-Origin). CORS es el mecanismo que permite que un frontend en localhost:3000 llame a una API en localhost:8080.

¿Por qué no lo nota Postman? CORS solo aplica a peticiones desde navegadores, no a herramientas como Postman o curl — por eso en Postman siempre funciona aunque CORS no esté configurado.

@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")   // aplica a todos los endpoints /api/
            .allowedOrigins("*")          // dev: cualquier origen
            // prod (Fase 8): .allowedOrigins("https://mi-app.com")
            .allowedMethods(
                "GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .exposedHeaders("X-Total-Count") // header personalizado legible en JS
            .maxAge(3600);              // cache del preflight 1 hora
    }
}

8. Paginación, Filtros y Sorting
@RequestParam · pagina · tamanio · ordenarPor · PageResponse<T>

¿Por qué paginar? Una API que retorna 10.000 registros en una sola respuesta es inusable. La paginación permite al cliente solicitar subconjuntos: "dame la página 0 con 10 elementos".

// Endpoint con paginación + filtros + sorting combinados
// GET /api/tareas?pagina=0&tamanio=2&categoria=TRABAJO&ordenarPor=prioridad

@GetMapping
public ResponseEntity<PageResponse<TareaResponse>> listarTareas(
        @RequestParam(required = false) String estado,
        @RequestParam(required = false) String categoria,
        @RequestParam(defaultValue = "0")  int pagina,
        @RequestParam(defaultValue = "10") int tamanio,
        @RequestParam(defaultValue = "fecha") String ordenarPor) {

    // 1. Construir filtro desde query params
    TaskFilter filtro = new TaskFilter(
        resolverEstado(estado), Optional.empty(),
        resolverCategoria(categoria), Optional.empty()
    );

    // 2. Paginar: skip + limit internamente (Fase 1)
    var pageResult = taskService.listarPaginado(pagina, tamanio, filtro);

    // 3. Ordenar el contenido de la página
    List<Task> ordenado = "prioridad".equalsIgnoreCase(ordenarPor)
        ? taskService.ordenarPorPrioridad(pageResult.contenido())
        : taskService.ordenarPorFecha(pageResult.contenido());

    // 4. Convertir Task → TareaResponse (DTO)
    var dtos = ordenado.stream().map(TareaResponse::fromTask).toList();

    // 5. Retornar PageResponse con metadatos de paginación
    return ResponseEntity.ok(PageResponse.from(new PageResult<>(
        dtos, pagina, tamanio, pageResult.totalElementos())));
}

URLs disponibles:

10. @RequestBody — Deserialización de JSON
Jackson · JSON → DTO automático · Content-Type: application/json

¿Qué es? @RequestBody indica a Spring que deserialice el cuerpo JSON de la petición HTTP a un objeto Java. Jackson (incluido en Spring Boot) hace la conversión automáticamente.

// El cliente envía este JSON en el body del POST:
// {"titulo":"Mi tarea","prioridad":"ALTA","categoria":"TRABAJO","usuarioId":1}

// Spring + Jackson lo convierte automáticamente a:
@PostMapping
public ResponseEntity<TareaResponse> crearTarea(
        @Valid @RequestBody CrearTareaRequest request) {
    // request.getTitulo()   → "Mi tarea"
    // request.getPrioridad() → Priority.ALTA
    // request.getUsuarioId() → 1L
}

// El Content-Type: application/json en el header de la petición
// le dice a Spring qué deserializador usar (Jackson)
// Postman lo agrega automáticamente cuando seleccionas "raw → JSON"
