🏗️ ¿Qué se construyó en esta fase?

Se agregó una suite completa de pruebas automatizadas a TaskFlow. Hasta la Fase 5 la aplicación funcionaba correctamente pero no tenía ningún test — era imposible verificar automáticamente que los cambios futuros no rompen el comportamiento existente. En esta fase implementamos 35 tests en 5 clases, cubriendo todas las capas: dominio puro (Mockito), capa JPA (@DataJpaTest), capa web (@WebMvcTest), integración total E2E (@SpringBootTest) y smoke test. La mayor dificultad fue la combinación de Spring Boot 4.1.1 + Spring Security 7, que requirió una solución de 3 piezas no documentada oficialmente.

📚 Conceptos Aplicados — Tutorial

1. Tests Unitarios con Mockito — @ExtendWith(MockitoExtension)

Los tests unitarios prueban una sola clase en completo aislamiento. No levantan Spring, no tocan la BD, no hacen llamadas reales. @Mock crea un objeto simulado del colaborador; @InjectMocks inyecta todos los mocks en la clase bajo prueba. Son los tests más rápidos (millisegundos) y forman la base de la pirámide.

// TaskJpaServiceTest.java — tests sin contexto Spring
@ExtendWith(MockitoExtension.class)     // activa Mockito, sin Spring
@DisplayName("TaskJpaService — Tests Unitarios")
class TaskJpaServiceTest {

    @Mock  private TaskRepository taskRepository;    // colaborador simulado
    @Mock  private UserRepository userRepository;    // colaborador simulado
    @InjectMocks private TaskJpaService taskJpaService; // clase bajo prueba

    @Test
    @DisplayName("crear: request válido → retorna TareaResponse con datos correctos")
    void crear_requestValido_retornaTareaResponse() {
        // ARRANGE — preparar datos y comportamiento del mock
        when(userRepository.findById(1L)).thenReturn(Optional.of(usuarioPrueba));
        when(taskRepository.save(any(TaskEntity.class))).thenReturn(tareaPrueba);

        // ACT — ejecutar el método bajo prueba
        TareaResponse response = taskJpaService.crear(request);

        // ASSERT — verificar resultado
        assertThat(response).isNotNull();
        assertThat(response.getTitulo()).isEqualTo("Tarea de prueba");
        verify(taskRepository, times(1)).save(any(TaskEntity.class));
    }

    @Test
    @DisplayName("cambiarEstado: desde estado COMPLETADA → lanza TaskStateException")
    void cambiarEstado_desdeCompletada_lanzaExcepcion() {
        tareaPrueba.setStatus(TaskStatus.COMPLETADA);
        when(taskRepository.findById(1L)).thenReturn(Optional.of(tareaPrueba));

        // assertThatThrownBy — AssertJ para verificar excepciones
        assertThatThrownBy(() -> taskJpaService.cambiarEstado(1L, request))
                .isInstanceOf(TaskStateException.class);
    }
}
2. @DataJpaTest — Slice de Repositorio

@DataJpaTest levanta solo la capa JPA: entidades, repositorios y una BD embebida. No levanta controllers, security ni services. Cada test corre en una transacción que se revierte al terminar — la BD siempre limpia. Permite probar queries derivadas, JPQL y Specifications con datos reales.

⚠️ Nota Spring Boot 4.x: TestEntityManager fue eliminado. Se usan directamente los repositorios para insertar datos de prueba. @DataJpaTest omite Flyway por defecto — se configura con ddl-auto=create-drop para que Hibernate genere el esquema desde las entidades.
@DataJpaTest
@ActiveProfiles("dev")
@TestPropertySource(properties = "spring.jpa.hibernate.ddl-auto=create-drop")
@DisplayName("TaskRepository — Tests @DataJpaTest")
class TaskRepositoryTest {

    @Autowired private TaskRepository taskRepository;
    @Autowired private UserRepository userRepository;

    @Test
    @DisplayName("findVencidas: retorna tareas con fechaLimite pasada y estado activo")
    void findVencidas_retornaTareasVencidas() {
        TaskEntity vencida = new TaskEntity(...);
        vencida.setFechaLimite(LocalDate.now().minusDays(5));  // pasada

        TaskEntity noVencida = new TaskEntity(...);
        noVencida.setFechaLimite(LocalDate.now().plusDays(10)); // futura

        taskRepository.save(vencida);
        taskRepository.save(noVencida);

        List<TaskEntity> resultado = taskRepository.findVencidas(
                LocalDate.now(), List.of(PENDIENTE, EN_PROGRESO));

        assertThat(resultado).hasSize(1);
        assertThat(resultado.get(0).getTitulo()).isEqualTo("Tarea vencida");
    }
}
3. @WebMvcTest — Slice de Controller

@WebMvcTest levanta solo la capa web: controllers, filtros y MockMvc. No levanta servicios ni repositorios reales — los dependencias se reemplazan con @MockitoBean (equivalente a @MockBean en Spring Framework 7, que eliminó el anterior). @WithMockUser simula un usuario autenticado sin generar un JWT real, ideal para probar reglas de autorización.

⚠️ Nota Spring Boot 4.x: En Spring Boot 4 el paquete cambió a org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest. @MockBean fue eliminado — se usa @MockitoBean de org.springframework.test.context.bean.override.mockito.
@WebMvcTest(TaskController.class)
@Import(TaskControllerWebMvcTest.TestSecurityConfig.class)
@DisplayName("TaskController — Slice Tests @WebMvcTest")
class TaskControllerWebMvcTest {

    @MockitoBean private TaskJpaService taskJpaService;  // reemplaza @MockBean
    @MockitoBean private JwtService jwtService;

    @Test
    @WithMockUser(roles = "USER")   // simula usuario autenticado sin JWT real
    @DisplayName("POST /api/tareas/db → 201 con cuerpo correcto")
    void crear_requestValido_retorna201() throws Exception {
        when(taskJpaService.crear(any())).thenReturn(tareaRespuesta);

        mockMvc.perform(post("/api/tareas/db")
                        .with(csrf())
                        .contentType(APPLICATION_JSON)
                        .content(objectMapper.writeValueAsString(req)))
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.titulo").value("Tarea de prueba"))
                .andExpect(jsonPath("$.estado").value("PENDIENTE"));

        verify(taskJpaService).crear(any());
    }

    @Test
    @WithMockUser(roles = "USER")
    @DisplayName("DELETE con rol USER → 403 Forbidden")
    void eliminar_conRolUser_retorna403() throws Exception {
        mockMvc.perform(delete("/api/tareas/db/1").with(csrf()))
                .andExpect(status().isForbidden());  // regla hasRole("ADMIN")
    }
}
4. @SpringBootTest — Test de Integración E2E

@SpringBootTest levanta el contexto completo de Spring: BD H2, Flyway, Security, todos los beans. Junto con @AutoConfigureMockMvc, simula peticiones HTTP reales sin servidor. @TestMethodOrder + @Order garantiza un flujo secuencial: registrar → login → crear → listar → cambiar estado → eliminar.

@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("dev")
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
@DisplayName("TaskController — Test E2E Integración")
class TaskControllerIntegrationTest {

    // Tokens y IDs compartidos entre tests del flujo
    private static String tokenUser;
    private static String tokenAdmin;
    private static Long tareaCreada;

    @Test @Order(1)
    @DisplayName("E2E Paso 1a: GET sin token → 401")
    void sinToken_retorna401() throws Exception {
        mockMvc.perform(get("/api/tareas/db"))
                .andExpect(status().isUnauthorized())
                .andExpect(jsonPath("$.status").value(401));
    }

    @Test @Order(2)
    @DisplayName("E2E Paso 1b: register → 201 con token")
    void register_retorna201ConToken() throws Exception {
        MvcResult result = mockMvc.perform(post("/auth/register") ...)
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.token").isNotEmpty())
                .andReturn();
        // guardar token para el resto del flujo
        tokenUser = objectMapper.readTree(result.getResponse()
                .getContentAsString()).get("token").asText();
    }

    @Test @Order(8)
    @DisplayName("E2E Paso 6a: DELETE con rol USER → 403")
    void delete_conRolUser_retorna403() throws Exception {
        mockMvc.perform(delete("/api/tareas/db/" + tareaCreada)
                        .header("Authorization", "Bearer " + tokenUser))
                .andExpect(status().isForbidden());
    }

    @Test @Order(9)
    @DisplayName("E2E Paso 6b: DELETE con rol ADMIN → 204")
    void delete_conRolAdmin_retorna204() throws Exception {
        mockMvc.perform(delete("/api/tareas/db/" + tareaCreada)
                        .header("Authorization", "Bearer " + tokenAdmin))
                .andExpect(status().isNoContent());  // 204
    }
}
5. Hallazgo técnico crítico — Spring Boot 4.1.1 + Spring Security 7 + @WebMvcTest

Esta combinación presenta un comportamiento no documentado oficialmente que requirió una solución de 3 piezas. Es el problema más complejo de esta fase y un conocimiento clave para cualquier proyecto SB4.

Problema 1: @EnableWebSecurity en @Configuration importada → 404 en todos los controllers

Usar @EnableWebSecurity en la inner class TestSecurityConfig deshabilita la auto-configuración de WebMvc de Spring Boot. El DispatcherServlet no registra los controllers → todos los requests devuelven 404 No static resource api/tareas/db.

Problema 2: Sin @EnableWebSecurity → No qualifying bean of type 'HttpSecurity'

Sin @EnableWebSecurity, Spring no registra el bean HttpSecurity necesario para construir el SecurityFilterChain en el TestSecurityConfig. El contexto falla al arrancar.

Problema 3: @WithMockUser sin efecto → todos los requests dan 401

Cuando la security config se importa manualmente, el SecurityMockMvcConfigurer no se aplica automáticamente al MockMvc de @WebMvcTest. @WithMockUser no inyecta el SecurityContext → todos dan 401.

✅ Solución: 3 piezas combinadas

Pieza 1 — @WebMvcTest(excludeAutoConfiguration = SecurityAutoConfiguration.class)
Evita cargar el SecurityConfig real (con JwtAuthenticationFilter) que bloquearía todos los requests.

Pieza 2 — @ImportAutoConfiguration(ServletWebSecurityAutoConfiguration.class)
Provee el bean HttpSecurity necesario para el TestSecurityConfig, sin traer la config real. Este auto-config contiene un inner EnableWebSecurityConfiguration con @EnableWebSecurity que registra el bean HttpSecurity.

Pieza 3 — MockMvcBuilders.webAppContextSetup(wac).apply(springSecurity()).build() en @BeforeEach
Aplica el SecurityMockMvcConfigurer que conecta @WithMockUser con el SecurityContext de cada request, sin perder los auto-configurers de @WebMvcTest (message converters, exception resolvers, etc.). 

// Solución completa — TestSecurityConfig + anotaciones de la clase
@WebMvcTest(
    value = TaskController.class,
    excludeAutoConfiguration = SecurityAutoConfiguration.class  // Pieza 1
)
@Import(TaskControllerWebMvcTest.TestSecurityConfig.class)
@ImportAutoConfiguration(ServletWebSecurityAutoConfiguration.class) // Pieza 2
class TaskControllerWebMvcTest {

    @TestConfiguration
    static class TestSecurityConfig {
        @Bean
        public SecurityFilterChain testSecurityFilterChain(HttpSecurity http) {
            http.csrf(disable).sessionManagement(STATELESS)
                .exceptionHandling(ex -> ex
                    .authenticationEntryPoint((req, res, e) ->
                        res.sendError(SC_UNAUTHORIZED))  // → 401 (no 403)
                )
                .authorizeHttpRequests(auth -> auth
                    .requestMatchers(DELETE, "/api/tareas/**").hasRole("ADMIN")
                    .anyRequest().authenticated()
                );
            return http.build();
        }
    }

    @Autowired private WebApplicationContext wac;
    private MockMvc mockMvc;

    @BeforeEach
    void setUp() {
        mockMvc = MockMvcBuilders             // Pieza 3: construir MockMvc manual
                .webAppContextSetup(wac)
                .apply(springSecurity())      // conecta @WithMockUser con SecurityContext
                .build();
    }
}

→
.apply(springSecurity()): registra el SecurityMockMvcConfigurer que conecta @WithMockUser con el SecurityContext de cada request del test.
@SpringBootTest E2E
→
Flyway ejecuta las 3 migraciones (V1 tablas, V2 datos, V3 seguridad). Los datos de ana@taskflow.com con rol ADMIN están disponibles para el flujo E2E.

→
Permite el flujo E2E: el token obtenido en el paso 2 (register) se guarda en un campo static y se reutiliza en los pasos 4-9 sin necesidad de re-autenticar.
